AFLALO Pull Portal

How the team borrows inventory from the NYC stock without draft orders. A requester fills one form, Sarena or Lillian approve each item, the approved units are reserved in Shopify so the website can't sell them while they're out, and the hold is released when the pieces come back. This page is the one place for the whole project: what it is, how it works, what it runs on, and everything you need to hand it to someone else.

Your email Must be an @aflalonyc.com address. Other domains are refused. Who approves Sarena or Lillian, item by item, in Airtable. Returning Use the return link in your confirmation email. It is already filled in for your pull.

Up to five items per pull, one to five units each. Only products that are active on the website can be pulled. If you ask for more than NYC has, that item is marked short right away and you get an email saying how many there actually are.

Why it exists, and why it's built this way

The problem. Internal pulls (stylist and celebrity loans, design reference, photoshoots) were tracked with Shopify draft orders. A draft order has no approval step, no return date, and no owner. People forgot to return pieces or forgot to cancel the draft, and the inventory numbers lied.

What's different about this solution

  • It uses Shopify's own reservation state, not a workaround. Shopify tracks inventory in named states: available, reserved, committed, on hand. Approving a pull moves units from available to reserved through the official inventory-move API, with the reason Shopify itself defines for reservations. The website sells against available, so a reserved unit physically cannot be oversold while it's out. Returning it is the reverse move.
  • Every reservation names its request. Shopify requires a ledger document for any non-available move. The worker writes the pull's own Airtable URL there. Open Shopify's inventory history on any variant and each held unit says which pull holds it and since when. That audit trail is exactly the discipline draft orders lacked.
  • Approvals can't double-book. Each move states the quantity it expects to find first. If two approvals race for the last unit, or something sells between the check and the move, Shopify refuses the second move instead of going negative, and the worker reports Insufficient stock rather than guessing.
  • Humans only ever make decisions. The requester fills two forms. Approvers change one dropdown per item. Nobody types counts, sends emails, or touches Shopify by hand.
  • No AI anywhere. The worker is a fixed sequence that runs every five minutes. Same input, same output, every time. It is the only thing that talks to Shopify, and it either does the exact move it logged or refuses and says why.
  • The forms are ours. Airtable's form builder can't do several items each with a quantity, or a searchable item picker with live counts. So the portal serves its own two web pages. They write straight into the Airtable base, and the team keeps working in Airtable as before.

The workflow

Five steps, in order. Only two people ever do anything: the requester and an approver (Sarena or Lillian). Everything in the "then, automatically" column happens on its own within about five minutes.

StepWhoDoes whatThen, automaticallyItem status
1 Requester Fills the request form: up to 5 items with quantities, a reason, what it's for, an expected return date, the passcode. One row per item is created and checked against live NYC stock. Sarena and Lillian get one email listing every item with its count and an approve link. The requester gets a confirmation with their return link. Any item asking for more than NYC has is marked short and the requester is told the real count. Requested
or Insufficient stock
2 Sarena or Lillian In Airtable, sets each item's Status to Approved or Denied (with a reason). Items on one pull are decided one by one. Denied: the requester gets the reason by email. Approved: the units are reserved in Shopify, so the website can't sell them. Decided By records who decided. Reserved
or Denied
3 Nobody The pieces are out. Nothing to do. On the return date the requester gets a reminder with the return form. Past it, the item shows OVERDUE, the requester gets a daily email (Sarena and Lillian copied), and the approvers get a 9am digest of every overdue item. Reserved
+ OVERDUE tag if late
4 Requester Opens the return link from any of their emails and answers the return form: Yes they're back, or Not yet, plus condition notes. A Yes flips the pull's reserved items to Return submitted. Sarena and Lillian get the answer, and the item stays on their 9:10am "returns waiting on you" email until one of them accepts it. Return submitted
5 Sarena or Lillian Checks the pieces and sets the item's Status to Return accepted, or Write-off if it isn't coming back. Accepted: the hold is released and the units are sellable again. Write-off: the units move to Shopify's damaged bucket, never sellable. Closed At is stamped. Closed

A pull reads Closed once every item on it is closed, by whatever path: accepted, denied, short, or written off. Partial approval is normal. Only approved items are ever reserved, and a Yes on the return form only affects items that were actually out.

Return form

Lives at /return/<pull> and is reached from the link in the requester's emails, so the pull is already filled in. It asks Returned? (Yes, they're back / Not yet), condition notes, and the passcode. Each answer is processed once.

The Airtable base

Base: AFLALO Inventory Pulls. Four tables. Two forms, two tables: the request form writes Pull Orders, the return form writes Pull Returns. Nobody types into the other two by hand.

TableOne row isWritten byWhat it's for
Pull Ordersone form submission, a "pull"the request formThe pull as a whole. Items column lists everything asked for with counts (short asks marked). State is Pending, Open, or Closed. Return form link is pre-filled for this pull. Every email is built from this row.
Pull Requestsone item on a pullthe workerWhere Sarena and Lillian work. Each item has its own Status, State, Overdue tag, Worker Log, and Decided By. Linked back to its pull.
Pull Returnsone return-form answerthe return formThe requester's word that the pieces are back, with condition notes.
Pull Inventoryone variant (style, color, size) at NYCthe worker, every passLive counts from Shopify. The form's pickers search this list. Gift cards excluded. Retired variants drop to 0.

Common changes

You want toDo this
Pause all inventory movesRailway → portal → Variables → remove WORKER_LIVE. The forms keep working, the worker goes to dry run. Set it back to 1 to resume.
Change the passcodeSet a new PORTAL_PASSCODE on Railway. It applies on the redeploy a minute later. Update the local .env and this page.
Add a reasonEdit the REASONS list at the top of worker.py and push. Adding the option in Airtable alone isn't enough, the form validates against the code's list.
Change approversEdit the To field on the automations above. The code doesn't know who approves.
Pull from a different locationSet PORTAL_LOCATION_NAME to the exact Shopify location name.
Move the siteSet PORTAL_URL, then run worker --return-form-url <new url> once so existing pulls' return links follow.
See where every pull standsLocally: python -m aflalo_pulls.worker --flow. It prints each pull's step and its exact next action.
Read what the worker didRailway → portal → Deploy logs. Lines start with worker:. Each item row also has a Worker Log column in Airtable.

Optional cleanup in Airtable

Checked live on Sep 30: every automation is published and valid, and the old Form view on Pull Requests is gone. Nothing is required. Two leftovers from the September redesign remain and are purely cosmetic. Delete them whenever convenient, or never.

  • On Pull Requests, the Status option Returned is unused. It was replaced by Return accepted. No row carries it and the code never sets it.
  • Four empty columns can go: Item (legacy text) and Quantity (legacy) on Pull Requests, and the two renamed (broken link, safe to delete) on Pull Requests and Pull Returns. The code tolerates their absence.

What you seeWhyFix
No alert email after a submitAutomation off, or the worker hasn't passed yetWait five minutes. Then check the automation is on and its To field.
A pull sits at PendingThe worker hasn't run since the submitNormal for up to five minutes. Longer: check Railway deploy logs.

Form says the passcode is wrongTypo, or the passcode was rotatedCheck the passcode at the top of this page.

Emails in spamFirst-time Airtable senderMark not-spam once.
